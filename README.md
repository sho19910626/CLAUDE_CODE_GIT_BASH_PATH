# 採用マーケティング支援アプリ

Indeed 運用代行の仕事を、営業から掲載後の分析まで 1 つの Next.js アプリにまとめています。

| ツール | パス | 用途 |
|---|---|---|
| **トップ** | `/` | 3 つのツールへの入口 |
| **営業コンソール** | `/console.html` | フォーム営業のターゲットリストと、企業ごとの営業文面の生成 |
| **Indeed 提案スタジオ** | `/indeed/studio` | ヒアリング内容から「棲み分け」戦略・キャッチコピー・撮影指示・Indeed掲載原稿を一括生成 |
| **Indeed 求人診断** | `/indeed` | 表示数・クリック数・応募数を入れると、どこが良くないか・どうすればいいかがその場で出る |

営業 → 提案 → 掲載 → 分析 を 1 つのサイトで完結させるための構成です。ログインは全ツール共通で 1 回だけ行います。

営業コンソールで商談化した企業は、**「提案スタジオへ引き継ぐ」**を押すと、企業名・業種・勤務地・Indeedの掲載状況が入った状態で提案スタジオが開きます。同じサーバーに同居しているため、コピーや貼り付けは要りません。

# Indeed 提案スタジオ (`/indeed/studio`)

お客様へのヒアリング内容を入力すると、Indeedに掲載する求人の提案一式を出力します。
**アルバイト・パート / 正社員(中途) / 正社員(新卒) / 契約・派遣・業務委託** に対応し、雇用形態ごとに訴求軸と原稿の書き方が切り替わります。

## 核となる考え方 — 「棲み分け」

このツールは応募数を増やすためのものではありません。**勝てない土俵から降りて、自社が一番になれる土俵に移る**ための求人を設計します。設計思想の原典として、JA(農協)の採用事例をAIに教え込んでいます。

> JAは「金融機関に興味がある人材」を採ろうとしていた。しかし金融志望者は都市銀行→地方銀行→信用金庫と受けて、最後の滑り止めにJAを受ける。つまりJAは競合すべてに落ちた人を採用していた。
> 実際に活躍している職員を観察すると、彼らは「金融が好きな人」ではなく「農家のおばあちゃんと縁側でお茶を飲むのが好きな人懐っこい人」だった。
> そこでキャッチコピーを「おばあちゃんと縁側でお茶を飲む仕事です」に変え、原付であぜ道を走る職員が縁側でお茶を飲む写真を載せた。すると応募者の質が一変し、「金融志望者の最下層」ではなく「人懐っこい人材の最上位層」を採れるようになった。

この構造を踏襲し、AIは次の手順で提案を組み立てます。

1. いま戦っている土俵を特定し、その中で何番目なのかを忖度せず言語化する
2. ヒアリングにある「活躍している人の特徴」「エピソード」から、その会社にしか言えない**仕事の再定義**を導く
3. 新しい土俵を宣言し、**あえて来なくていい人**まで明言する
4. 職種名・キャッチコピー・写真・原稿本文・応募時の質問まで、すべてを新しい定義に揃える

## 出力される提案

| タブ | 内容 |
|---|---|
| **① 棲み分け戦略** | 現状分析(戦っている土俵・立ち位置・勝てない理由・放置した場合のリスク) / 仕事の再定義 / 新しい土俵 / ターゲット人材の人物像と検索行動 / 棲み分けの根拠 / 切り捨てる人 |
| **② 職種名・コピー** | Indeed職種名の推奨案+別案3つ+埋め込む検索キーワード / キャッチコピー5案(情景型・逆説型・引用型・数字型・呼びかけ型)と、それぞれの狙いと使いどころ |
| **③ ビジュアル** | メインカットの撮影指示書(シーン・被写体・構図・光・トーン) / 掲載カットリスト4〜6枚と各カットの役割 / 撮ってはいけない写真 / AI画像生成(OpenAI APIキー設定時) |
| **④ 掲載原稿** | Indeedにそのまま貼れる完成原稿(職種名・仕事内容600〜1000字・訴求ポイント・1日の流れ・応募資格・募集要項・選考フロー・FAQ)。全文コピー / .txtダウンロード |
| **⑤ 運用・チェック** | KPI設計 / スポンサー予算の考え方 / A/Bテスト案 / 運用のポイント / 応募時に聞くべき質問 / 掲載前の法令チェック |

提案書全体は Markdown でコピー・ダウンロードでき、そのまま顧客への提案資料になります。

## ヒアリング項目

**★印の2項目が提案の質を決めます。** 棲み分けは活躍者の観察からしか導けないためです。

- 基本情報 — 企業名 / 企業HP・採用サイトURL(内容を自動で読み取ります) / 事業内容 / 募集職種 / 勤務地
- **★ 棲み分けの材料** — 実際に活躍している人の特徴 / 活躍している人の具体的なエピソード / すぐ辞めた人の特徴 / 職場の雰囲気
- 採用の現状 — 採用競合 / 現在の採用課題 / これまでの訴求内容 / 採用人数・時期・予算
- 募集条件 — 給与 / 勤務時間・シフト / 休日 / 福利厚生 / 応募条件 / 選考フロー
- 職場の写真(最大3枚・任意) — AIが空気感を読み取り、棲み分けと撮影指示に反映します

未入力の項目はAIが業種から補完しますが、**給与や数字は捏造せず「面談時にご案内します」と書きます**。追加でヒアリングすべき事項は⑤タブの「掲載前チェック」に出力されます。

フォーム下部の「サンプル(JA事例)を入力してみる」を押すと、上記のJA事例がヒアリングシートに入り、棲み分けがどう機能するかを試せます。

## Indeedというメディアへの最適化(AIに組み込み済み)

- Indeedは検索エンジン型のため、職種名の先頭には**検索される一般名詞**を置き、その後ろに棲み分けを表す一言を足す
- 求職者が見るのは【職種名 → 給与・勤務地 → 画像 → 仕事内容の冒頭3行】の順。ここで離脱が決まる前提で原稿を組む
- 8割以上がスマートフォン閲覧。1文を短く、段落を細かく、空行を多めに
- 「急募!!」「稼げる!」などの煽り表現・記号の羅列は品質評価を下げるため使わない
- 職業安定法・男女雇用機会均等法・雇用対策法により、年齢・性別・国籍を限定する表現を書かない。「若手歓迎」「主婦歓迎」「女性活躍中」も避け、事実の記述(「入社1〜3年目が中心です」)に置き換える

## Windows でダブルクリック起動する

初回のセットアップが済んでいれば、以降は **`start-app.bat` をダブルクリック**するだけで起動できます。ターミナルを開く必要はありません。

やっていることは3つです。

1. 依存関係が入っていなければ `npm install` を実行
2. 開発サーバーを起動
3. サーバーの応答を待って、既定のブラウザで `/indeed`(求人診断)を開く

黒い画面が出たままになりますが、**これがサーバー本体**なので開いたままにしてください。閉じるとアプリが止まります。

**デスクトップにショートカットを作る**

`start-app.bat` を右クリック → 「送る」→「デスクトップ (ショートカットを作成)」。作られたショートカットは自由に名前を変えられます（右クリック →「プロパティ」→「アイコンの変更」でアイコンも変えられます）。

## チームで使う(1台を社内で共有する)

**`start-shared.bat` をダブルクリック**すると、同じ社内ネットワークにいる人が自分のブラウザから使えるようになります。使う人の側でのインストールは不要です。

起動すると、黒い画面に伝えるべきURLが表示されます。2つのツールが同じサーバーから配信されるため、どちらもそのまま共有できます。

```
 他の人には、このURLを伝えてください:  (イーサネット)

   営業コンソール       http://192.168.1.23:3000/console.html
   Indeed 提案スタジオ  http://192.168.1.23:3000/indeed/studio
```

画面の上部にお互いへのリンクがあるので、どちらか一方を伝えれば行き来できます。

外部サービスへの登録も、月額費用もかかりません。APIキーもこの1台に置いた1つで済みます。

**条件**

- 使う人が**同じ社内ネットワーク**にいること(社外・在宅からは使えません)
- 起動した**1台を立ち上げっぱなし**にしておくこと。黒い画面を閉じると全員使えなくなります
- 初回に Windows のファイアウォールが確認を出したら**「アクセスを許可する」**を選ぶこと。許可しないと他の人から見えません

**パスワードをかける場合**

`.env` に `APP_PASSWORD` を書くと、`middleware.ts` がすべてのページとAPIをログイン必須にします。社内ネットワーク内だけなら省略しても構いませんが、**インターネットに公開する場合は必須**です。ローカル開発(`NODE_ENV !== "production"`)で未設定のときだけ、毎回ログインせずに済むよう素通しになります。本番で未設定にすると誰もログインできません。

以前あった `BASIC_AUTH_USER` / `BASIC_AUTH_PASSWORD` は廃止し、`APP_PASSWORD` に一本化しました。ログイン時に入力するのは**お名前と共通パスワード**の 2 つで、お名前は「誰が実績を取り込んだか」の記録に使われます。

**環境変数の一覧**

| 変数 | 要否 | 内容 |
|---|---|---|
| `ANTHROPIC_API_KEY` | 必須 | Anthropic APIキー |
| `APP_PASSWORD` | 必須 | ログインの署名鍵。最初の管理者を作るときの合言葉も兼ねる。変更すると全員がログアウトする |
| `DATABASE_URL` | 必須 | データとアカウントの置き場(Neon)。**本番では未設定だと起動しません**(顧客データを1台のディスクに置かせないため) |
| `ANTHROPIC_MODEL` | 任意 | 省略時は `claude-opus-5` |
| `OPENAI_API_KEY` | 任意 | 提案スタジオのAI画像生成を使う場合 |

**営業コンソールとの連携**

共有で使う場合は、営業コンソールの「連携先」欄に共有用のURL(`http://192.168.x.x:3000/indeed/studio`)を入れてください。引き継ぎURLがその宛先で作られます。

## インターネットに公開する(Vercel の無料枠)

PCを起動しておく必要がなく、在宅や外出先からも使えます。無料枠で動きます。

**なぜ動くのか**

生成は3段階に分かれており、**段階ごとに別のリクエスト**として呼び出します(順番は画面側が管理)。1回あたり1〜2分に収まるため、サーバーレスの実行時間制限に収まります。`app/api/indeed/route.ts` の `maxDuration = 300` がその上限です。

```
① strategy(戦略)  →  ② jobpost(原稿) と ③ visual(ビジュアル・運用) を並列
```

**手順**

1. [vercel.com](https://vercel.com) に GitHub アカウントでサインアップ(支払い登録は不要)
2. **Add New → Project** から このリポジトリを選ぶ
3. **Branch** に公開したいブランチを指定する
4. **Environment Variables** に下記を入れる(最低でも `ANTHROPIC_API_KEY` と `APP_PASSWORD`。求人診断を全員で共有するなら `DATABASE_URL` も)
5. **Deploy** を押す。数分で `https://＜プロジェクト名＞.vercel.app` が発行される
6. `/indeed` を開き、パスワードを入力して動作を確認する
7. 営業コンソールの「連携先」欄に `https://＜ドメイン＞/indeed/studio` を入れる

**公開するときは `APP_PASSWORD` と `DATABASE_URL` の両方が必須です。**

- `APP_PASSWORD` … ログインの署名に使う鍵。最初の管理者を作るときにだけ、合言葉としても入力します
- `DATABASE_URL` … データとアカウントの置き場。**未設定だと本番は起動しません**。顧客企業名・実績数値・営業リストを1台のディスクに置かせないための決まりです

初回に `/indeed` を開くと「最初の管理者を作る」画面が出ます。お名前・パスワード(12文字以上)・`APP_PASSWORD` の値を入れると管理者ができます。
以降のアカウントは、管理者が **/indeed/admin** から 1 人ずつ発行します。チームには **URL と、その人ぶんのお名前・パスワード** を伝えてください。

退職・異動があったら、`/indeed/admin` でそのアカウントを **停止** します。全員のパスワードを変える必要はありません。

## うまく動かないとき

```bash
node check-key.js
```

`.env` の書き方、APIキーの有効性、実際に使うモデルで生成できるか、その所要時間までを診断します。**APIキーの中身は表示しない**ので、結果はそのまま共有できます。

## 使い方のコツ

- **企業HPのURL**: トップページのURLを入れると、AIが事業内容・トーンを自動分析します
- **企業イメージ**: ターゲット層・ブランドの雰囲気・強みを書くほど精度が上がります
- **文言**: キャンペーン情報や期限など、画像に必ず入れたい内容を書いてください
- 生成後もテンプレートを切り替えてデザインの候補を比較できます
- **「✨ AI写真」テンプレート**を選ぶと、ブランドに合わせた写真背景をその場で生成します(OpenAI APIキーが必要。1枚あたり数円〜数十円の従量課金)
- リール動画は「AI写真背景」に切り替えるとKen Burns効果(ゆっくりズーム)付きの写真背景になります
- リールは映像素材があるほど本領を発揮します。Sora のAI動画、またはご自身で撮影した動画のアップロードをおすすめします
- 文字を主役にしたスライド演出の動画がほしいときは、ストーリータブの「🎬 動くストーリー」を使ってください
- OpenAIの新しい画像モデルが出たら `.env` の `OPENAI_IMAGE_MODEL` を変えるだけで切り替えられます

# Indeed 求人診断 (`/indeed`)

**表示数・クリック数・応募数の 3 つを入れると、その場で「どこが良くないか」「どうすればいいか」が出ます。**
登録も保存もログインも不要です。

画面は 2 つあります。

| 画面 | パス | 用途 |
|---|---|---|
| **診断** | `/indeed` | スプレッドシートを貼り付けるか、数字を手で入れて診断する(要ログイン) |
| **記録して学習させる版** | `/indeed/manage` | 求人ごとに実績を積み上げ、施策の効果を測って提案の精度を上げる |

まずは `/indeed` を使ってください。毎月の記録をためて学習させたくなったら `/indeed/manage` に進みます。

## チームで共有する

複数人で同じデータを見て、同じ学習結果を使えるようにできます。

| 保存先 | 条件 | 使い方 |
|---|---|---|
| **Postgres** | `DATABASE_URL` を設定 | 全員が同じデータを見る。インターネット公開向け |
| **ファイル** | 未設定(既定) | `.data/store.json` に保存。そのPCの中だけで完結 |

コードは同じです。環境変数の有無で保存先が切り替わるので、

### 公開手順(Vercel + Neon・どちらも無料枠)

**1. データベースを用意する**

<https://neon.tech> でアカウントを作り、プロジェクトを新規作成します。
表示される接続文字列(`postgresql://...`)をコピーしてください。
テーブルは初回アクセス時に自動で作られるので、SQL を流す作業は不要です。

**2. Vercel にデプロイする**

<https://vercel.com> でこの GitHub リポジトリを Import します。
Environment Variables に次の 3 つを設定してください。

| 変数 | 値 | 必須 |
|---|---|---|
| `APP_PASSWORD` | チームで共有するログインパスワード | **必須** |
| `DATABASE_URL` | Neon の接続文字列 | **必須** |
| `ANTHROPIC_API_KEY` | AI 原稿提案を使う場合のみ | 任意 |

**3. 全員に URL とパスワードを配る**

`https://<プロジェクト名>.vercel.app/indeed` を開くとログイン画面が出ます。
お名前とパスワードを入れれば使えます。スマホからも開けます。

### ログインの仕組みと、その限界

6〜20人の社内チーム向けに、**共有パスワード + 表示名**という軽い方式にしています。
ひとりずつアカウントを発行する仕組みは運用の手間が大きく、この規模では続かないためです。

割り切っている点を正直に書いておきます。

- **全員が同じパスワードを使います。** 知っている人は誰でも入れます
- **表示名は自己申告です。** 編集記録は「なりすませない証明」ではなく、あとから経緯を辿るための記録として扱ってください
- **退職・異動があったらパスワードを変更してください。** 変更すると全員が再ログインになります

セッションは HMAC 署名つき Cookie で、改ざんすると API 側で必ず弾かれます(30日で失効)。
`APP_PASSWORD` が未設定のときはログインできないので、パスワードなしで公開されることはありません。

### だれが何をしたかの記録

取り込み・登録・削除はすべて記録され、画面下の「だれが何をしたか」で確認できます。

```
2026/8/16 8:26  佐藤  実績を取り込み       10 件
2026/8/16 8:26  山田  実績を取り込み       10 件
2026/8/16 8:26  山田  求人を登録・更新     【小牧市】フォークリフト/日勤のみ ほか2件
```

### 同時に触っても壊れないようにしている点

6〜20人で使う前提なので、**ストア全体を丸ごと上書きする API にはしていません。**
「求人を1件更新」「実績をまとめて取り込み」のように操作単位で送るため、
自分が画面を開いている間に他の人が加えた変更を、保存時に巻き戻してしまうことがありません。

実績は「求人 + 期間」で一意なので、2人が同じ日のデータを取り込んでも重複しません。

## お金の見立て（費用の列があるとき）

**利用金額**か**クリック単価**の列があると、応募単価まで踏み込んで診ます。

```
応募単価 = クリック単価 ÷ 応募率
```

応募単価が高いとき、原因が「クリックが高い」のか「応募率が低い」のかで打ち手はまったく別物です。

| 主因 | 何が起きているか | 何をすべきか |
|---|---|---|
| クリック単価 | 競合の多いキーワードで戦っている、入札が高すぎる | 入札・キーワード・エリア指定（管理画面側） |
| 応募率 | 原稿が読まれても応募につながっていない | 原稿と応募フロー（原稿側） |

ここを取り違えると、**原稿をいくら直しても単価は下がりません。**
そこで「クリック単価だけ相場に戻したらいくらになるか」「応募率だけ戻したらいくらか」を並べて出します。

### 「で、いくらにするのか」まで出す

診断で終わらせず、この求人の実数から具体策を組み立てます。

- **狙う入札額**（現在と相場の中間）と、そこまで下げたときのクリック増・応募増
- **職種名の言い換え案**（その求人の職種から組み立てた 3 案と、それぞれ競合が減る理由。すべて Indeed の掲載基準を満たす形で出します）
- 配信先の勤務地設定の絞り方（その求人の実際の都道府県を使う）
- 時給が相場より低い場合は、その差額と、引き上げ提案の目安額
- **クライアントへの伝え方**（報告書にそのまま貼れる一文）

見込みの数字は**相場まで一気に戻せる前提では出しません。**
単価が高いのは競合が強いからのことが多く、達成できない数字をクライアントに約束すると信用を失うためです。
目標は「現在と相場の中間」に置き、その前提も文章に明記します。

比較の相場は世間の平均値ではなく、**自社の同じ業種・職種の求人（3件以上）**から取ります。
単価はエリアと時期で大きく振れるため、他社の平均を基準に据えるほうが危険だからです。

日ごとの消化額がほぼ同額で並んでいる場合は、**日予算の上限に張り付いている**と判定します。
「表示が伸びない原因は原稿ではなく予算」だと分かるので、管理画面を見に行かなくても切り分けができます。


### 職種名の言い換えについて

Indeed の職種名は検索語との突き合わせに使われるので、クリック単価に直接効きます。
「フォークリフト」のような一般語だけだと、同じエリアの同職種すべてと同じ枠で競ることになります。

**ただし、絞り込む方法には Indeed の掲載基準による制約があります。**
基準では職種名に職種名以外を入れないことになっており、勤務地・給与・雇用形態・条件・記号を入れると
「質が低い」と判定されて検索露出が落ちます（スポンサー求人でしか出なくなることがあり、
その場合は無料の検索流入が止まります）。Indeed が挙げている NG 例がまさに
「コンビニスタッフ アルバイト（東京）時給1050円」の形です。

そこで、絞り込みは**仕事の中身だけ**で行います。推奨されている形は「●●の△△」です。

```
「物流倉庫でのフォークリフト」
  どこで何をするかの形。「フォークリフト」だけで探す人より競合が薄い

「リーチリフトオペレーター」
  職種名そのものを具体的な言い方に置き換える。応募までの距離が近くなる

「物流倉庫でのリーチリフトオペレーター」
  現場と仕事の両方。検索母数はいちばん小さいが、競合もいちばん薄い
```

31 職種それぞれに「現場・扱うものを表す語」と「仕事を具体化した職種名」を持たせています。
勤務地・給与・雇用形態はここに入れません（それぞれ専用の欄があり、検索にはそちらが使われます）。

**プロファイルに無い職種**（葬祭ディレクター、図書館司書など）では、案をでっち上げずに
「事例が無いので案は出せません」と明示したうえで、作り方と守るべき基準だけを渡します。
業種が分かる場合は、業種から「●●の」に入る語を出します。

診断側では逆方向のチェックもします。いま登録されている職種名に記号・勤務地・給与・雇用形態・
条件の言葉が入っていないかを調べ、入っていれば**基準に触れる部分を落とした形**を示します
（「【小牧市】フォークリフト 時給1,300円/正社員」→「まず『フォークリフト』まで削ってから、
仕事の中身を足してください」）。落として何も残らない職種名は、条件の羅列で職種名が
入っていないということなので、そう伝えます。

出すのは**型であって事実ではありません。**実態に当てはまらない言葉で集めても応募にはならないため、
その注意書きも必ず添えます。

## Indeed の CSV をそのまま貼れます

管理画面から落とした CSV は加工せずに貼り付けられます。
`案件名` `インプレッション数` `コンバージョン数` `利用金額` `クリック単価` `コンバージョン単価` といった
Indeed の実際の列名に対応しています。手作りのスプレッドシート（`求人名` `表示数` `応募数` など）も従来どおり使えます。

利用金額の列が無くても、クリック単価があれば **クリック単価 × クリック数** で費用を復元します。

## 入口は 2 つ

### 📋 スプレッドシートを貼り付け(おすすめ)

毎日つけている記録をコピーして、そのまま貼り付けるだけです。

```
日付        企業名   求人名                      業種      職種          雇用形態  都道府県  時給   表示数  クリック数  応募数
2026/08/03  ○○物流  【小牧市】フォークリフト   物流・…   フォークリフト  派遣     愛知県   1250   640     18        1
2026/08/04  ○○物流  【小牧市】フォークリフト   物流・…   フォークリフト  派遣     愛知県   1250   712     21        1
2026/08/03  △△ケア  介護スタッフ(夜勤なし)     介護・福祉  介護スタッフ   パート   大阪府   1200   310      9        0
```

- 必須は **求人名 / 表示数 / クリック数 / 応募数** の 4 列だけ
- **日付**の列があれば、毎日 1 行ずつの記録として取り込みます
- **企業名 / 業種 / 職種 / 雇用形態 / 都道府県 / 時給**の列があると、**その単位で学習します**
- 求人は「企業名 + 求人名」で同一と判断します(表記ゆれは吸収)
- 同じ求人・同じ日のデータを貼り直しても**二重計上になりません**。毎日まるごと貼り直す運用でも問題ありません
- タブ区切り(スプレッドシートからのコピペ)と CSV の両方、「1,234」「¥5,000」といった書式付きの数値にも対応

貼り付けたデータはブラウザに蓄積され、求人ごとの診断・企業ごとの傾向がすぐ表示されます。
求人行をクリックすると考察の全文が出ます。

### ✏️ 数字を手で入れる

その場の数字だけ見たいときはこちら。**1週間** か **1か月** を選び、
表示数・クリック数・応募数を入れると即座に診断が出ます(保存はされません)。

「詳しく入れる」を開くと、入れるほど提案が具体的になります。

- **前の週(月)の数字** → 「前回と比べてどう変わったか」が出ます(季節・連休の影響は差し引いて判定)
- **給与・掲載形態・職場写真・応募フォームの設問数** → 条件面の指摘が出ます
- **求人タイトル・キャッチコピー・仕事内容** → 文字数・構成・NG表現まで実際に照合して指摘します

## まず出るのは「考察」1 つ

求人を開くと、細かい数字より先にこれが出ます。

```
【一覧には出ているのに、選ばれていません】

クリック率が 1.0%(基準 2.8% の 36%)。60,000 回表示されて、クリックは 600 回だけです。

求職者が検索結果の一覧で見ているのは、タイトル・給与・勤務地・キャッチコピーの4つだけです。
詳細を開くかどうかはここで決まるので、この4つのどれかが並んでいる他社に負けている
ということになります。実際に確認できた範囲では、キャッチコピーに給与と休日・勤務時間の
記載がありません。詳細まで来た人の応募率は基準以上なので、中身は悪くありません。
入口の見せ方だけの問題です。

やること: 1) キャッチに給与と休日・勤務時間を入れる
          2) キャッチコピーを70文字まで使い切る
          3) タイトルに条件を1つ足す(未経験可・土日休みなど)

クリック率を基準並みまで戻せれば、月の応募は今の約 63.9 件から 176.3 件前後。
上位25%の水準まで持っていければ 264.5 件前後です(他の段階が今のままという前提の単純計算です)。
```

考察は 5 つのセクションで構成されます。

| セクション | 何を見るか |
|---|---|
| **現状** | 他社ベンチマークとの比較(横の比較)。集計期間の季節に合わせて基準を補正します |
| **推移** | 前期からどう変わったか(縦の比較)。季節要因を差し引いた実質の変化で判定します |
| **自社の他求人との比較** | 同職種の自社求人の中で何位か、上位の求人と何が違うか |
| **この企業の傾向** | その企業の求人が一貫して上振れ/下振れしているか(蓄積データから) |
| **原因の見立て** | 上の3つを踏まえて、なぜそうなっているのか |
| **職種ならではの見立て** | その職種・雇用形態で何が起きているのか、何を書けば効くのか |
| **時期について** | 今が動く時期か閑散期か、次の月に何が来るか |
| **見込み** | 直した場合の応募数、プラン全体をやりきった場合、次に効いてくる段階 |

そのままお客様への報告に使える文章になっています(コピーボタンつき)。
数字の内訳やベンチマークの粒度は、その下に畳んであります。

### 推移の分析 — `lib/indeed/trend.ts`

同じ「クリック率 2.7%」でも、先月 3.4% から落ちてきたのか、2.1% から戻してきたのかで
打つべき手はまったく変わります。落ちているなら原因の特定が先で、戻してきているなら今やっていることを続けるのが正解です。

指標の組み合わせから原因を読み分けます。

- **表示増 × CTR減** → 露出が広がって関心の薄い層にも出ている。予算を増やした直後なら想定内
- **表示横ばい × CTR減** → 競合が増えたか、原稿変更が逆効果。露出では説明がつかない
- **CTR増 × 応募率減** → 一覧での見せ方が実際の条件より魅力的すぎて、開いた人がギャップで離れている
- **表示が大幅減** → 予算・掲載順位・有効期限の問題。原稿ではない

変化した期間に施策を記録していれば突き合わせて、「その施策の後に悪化しているので戻すか切り分けを」まで言います。
3 期間以上あれば、一貫した下降・上昇も検出します。

### 企業ごとの学習 — `lib/indeed/benchmark.ts`

同じ職種・同じ雇用形態でも、クライアントによって成果は一貫して上下します
(知名度、職場環境、条件の出し方、応募対応の速さ)。

その企業の求人それぞれについて「同セグメントの基準ならこのくらいのクリックが出るはず」を
積み上げ、実測と比べます。求人の構成(業種・職種の偏り)に左右されない比較になります。

```
○○物流 の求人は 4 件・累計 82,000 表示ぶんのデータが貯まっています。
同じ職種・雇用形態の基準と比べると、この企業の求人は一貫して
クリック率が基準より 18% 下 に出ています。

いま詰まっている段階と同じ方向なので、この求人だけの問題ではなく企業側の要因
(知名度・条件水準・職場環境)が効いている可能性が高いです。原稿の微調整で
取り返せる幅は限られるため、条件そのものの見直しをクライアントに提案するほうが
早い場面です。
```

**詰まっている段階と企業の傾向が同じ方向かどうか**で、意味も打ち手も変わります。

- 同じ方向 → 企業側の要因。原稿ではなく条件の見直しをクライアントに提案する場面
- 逆方向 → その企業は本来その段階が強いので、今回はこの求人固有の要因
- 別の指標 → 今回の課題とは切り分けて考える

求人 2 件以上で表示し、データが貯まるほど確かになります(反映度も併記)。

### 自社の他求人との比較 — `lib/indeed/peers.ts`

ベンチマークは「同セグメントの平均はこのくらい」までしか教えてくれません。
現場で本当に知りたいのは「うまくいっている求人は、この求人と何が違うのか」です。

同職種・同雇用形態の自社求人の中で順位を出し、成績が上の求人と属性を突き合わせて差分を出します。

```
自社で登録している同職種・同雇用形態の求人 4 件中 4 位です
(クリック率 3.2%、最も高いのは「【春日井市】リフト/土日休み」の 5.5%)。

・成績が上の 3 件は給与の中央値が 1,400円。この求人は 1,250円 で、11% 低い水準です
・成績が上の 2 件は給与を「〜円」の範囲で見せています。この求人は単一提示です
・成績が上の 2 件は職場写真を載せています。この求人は未掲載です
・成績が上の 2 件はキャッチコピーに給与を書いています。この求人は書いていません
```

比較するのは給与・給与の上限表記・スポンサー掲載・職場写真・キャッチコピーの内容と長さ・
仕事内容の構成・応募フォームの設問数です。「上位群の過半数がそうしていて、この求人はそうしていない」
ものだけを挙げるので、当てはまらない指摘は出ません。

### 週次分析 — 月の中の凹みまで見る

集計単位は 1週間 と 1か月 から選べます。週次にすると、月次では平均に埋もれる
**月の中の凹み**が見えるようになります。

| 期間 | 季節指数 |
|---|---|
| 8月まるごと | 0.73 |
| **お盆の週 (8/10〜8/16)** | **0.52** |
| 8月最終週 (8/24〜8/30) | 0.80 |
| 年末年始の週 (12/28〜1/3) | 0.57 |
| GWの週 (4/29〜5/5) | 0.64 |

長期連休(お盆・年末年始・GW)にかかる日を安く見積もり、同じ月の他の日をそのぶん
高く見積もることで、**1か月ぶんを合計すると必ず月の指数に戻ります**(二重に効かせない)。
そのため、月次で見ている限り結果は今までと変わりません。

お盆の週に「応募が半減した」と出ても、それは指数 0.52 の週なので当然です。
週次分析では、その落ち込みを差し引いた実質の変化を出します。

### 季節変動の補正 — `lib/indeed/season.ts`

求人の成果は月で大きく上下します。これを無視すると 3 つが同時に壊れます。

1. **診断** — 8月の落ち込みを「原稿が悪い」と誤診する
2. **推移** — 7月→8月の自然な減少を「悪化した」と報告する
3. **効果測定** — 7月に打った施策を8月の数字で測って「効かなかった」と誤学習する

3 が特に厄介で、放置すると学習そのものが逆方向に進みます。そのため季節指数で補正しています。

```
8月はお盆をはさみ、年間で最も求職者が動かない月のひとつです。応募が落ちるのは
自然な変動で、原稿の問題とは限りません。この時期は例年 -9% 程度落ちるので、
以下の変化はその季節要因を差し引いた実質の値で見ています。

見かけ上は 表示数 -21% と動いていますが、季節要因を差し引くと 表示数 +3% で、
実質的には横ばいです。時期どおりの動きなので、この変化を理由に原稿を触る
必要はありません。
```

**「求人が多い時期」と「応募が多い時期」は別物**です。企業は 8〜10月に求人を出しますが
(10月入社・下期に向けて)、求職者は 8月のお盆には動きません。調べた記事の多くがこの 2 つを
混同していますが、このツールが扱うのは応募数なので**求職者側の動き**を採用しています。

**指標ごとに感応度を変えています。** 季節で変わるのは主に求職者の母数なので、影響が最も大きいのは
表示数(感応度 1.0)。クリック率は一覧に並んだ求人の中での相対的な選ばれ方なので母数が減っても
大きくは動かず(0.15)、応募率はその中間(0.4)としています。

業種・雇用形態ごとにカーブが変わります(調査結果と突き合わせて検算済み)。

| セグメント | ピーク | 底 | 12月 |
|---|---|---|---|
| 飲食 × アルバイト | **5月 (1.17)** | 8月 (0.80) | 0.80 |
| 物流 × 派遣 | 3月 (1.27) | 8月 (0.73) | 0.93 |
| 介護 × 正社員 | 1月 (1.21) | 5月 (0.83) | 0.83 |
| 販売 × 派遣 | 3月 (1.27) | 8月 (0.73) | **0.98** |

飲食だけ 5月がピークなのは、大学生の履修が確定してからバイトを探し始めるためです
(Indeed の調査で確認)。販売の 12月が落ちないのは、年末の短期バイト需要があるためです。

時期に応じた動き方の助言も出します。閑散期には「応募が少ないのは時期の問題なので、慌てて条件を
下げないでください。他社も掲載を控えるので出し続ければ埋もれにくい利点があります」、
繁忙期には「ここで取り切れないと年間計画に響きます」、そして必ず**次の月に何が来るか**を添えます。

> ⚠ 季節指数の初期値は、下記の記事ベースの定性情報から組み立てた推定値です。公開された月次指数ではありません。
> ベンチマークや施策効果と同じく、自社の実績が月をまたいで貯まるほど実測の指数に置き換わります
> (求人ごとに「その求人の全期間平均に対する各月の比」を取り、求人をまたいで平均するので、
> 求人の入れ替わりや規模の違いに影響されません)。

### 職種・雇用形態ならではの考察 — `lib/indeed/jobtype.ts`

「クリック率が低い」までは数字で分かりますが、その先の「なぜ低いのか」は職種で違います。

- **フォークリフト** — 有資格者という限られた母集団の取り合いなので、給与が相場を下回ると一覧の時点で外される
- **ナイトワーク** — 高時給が前提なので給与では差がつかない。むしろ「その時給が本当に貰えるのか」が疑われている
- **介護** — 売り手市場でクリックは集まるが、夜勤と人員配置が書いていないと応募されない
- **看護師** — 母数が小さく表示数が伸びないのは正常。露出を増やすより条件で確実に取るほうが効率的

31 の職種プロファイルを持ち、職種名と求人タイトルから判定します。それぞれに
「どんな人が応募してくる市場か」「段階ごとの見立て」「応募判断を分ける項目」を持たせています。

判定は上から順に、具体的な職種を先に見ます。「ホール」のように業種をまたぐ語があるため、
パチンコ・イベント・展示を先に外してから飲食を判定する、といった順序をプロファイル側に
持たせています（パチンコホールスタッフに飲食の見立てを出さないため）。

プロファイルに当たらない職種でも、雇用形態の見立てと数値診断は通常どおり出ます。
出ないのはその職種ならではの見立てだけで、その場合は職種名の案も「案は出せません」と
正直に伝えます（当てずっぽうの見立てを出すほうが害が大きいため）。

```
【フォークリフト】免許保有者に限られた、母集団の小さい市場です。有資格者は複数社に
登録していることが多く、条件を並べて比較されます。

有資格者は自分の資格に見合う時給の相場を正確に把握しているので、金額が相場を下回ると
一覧の時点で外されます。「リーチ」「カウンター」の別と、乗る比率をタイトルかキャッチに
入れてください。

派遣は「応募 = 派遣会社への登録」なので、応募のハードルが直接雇用より 1 段高くなります。
同一労働同一賃金の影響で時給が相場に収れんしやすく、金額だけでは差がつきにくい構造です。

この職種で応募判断を分けるのは「リーチ / カウンターの別」「リフトに乗る比率」
「扱う荷物の重さ」「資格取得支援の有無」「倉庫の温度環境」です。いまの原稿には
「リーチ / カウンターの別」「リフトに乗る比率」の記載が見当たらないので、
ここを書き足すのが最短です。
```

原稿を貼り付けると、その職種で必須の項目が書けているかを実際に照合して、
足りないものだけを挙げます。

雇用形態(派遣・正社員・アルバイト・契約・業務委託)ごとの見立ても重ねます。
「正社員は検討期間が長く、応募率がアルバイトより低いのは正常です」のように、
数字の読み方そのものが変わる点も伝えます。

職種特有の法令注意も持たせています。たとえばナイトワークは 18 歳未満を雇用できないため
「18歳以上(高校生不可)」の記載が法令上むしろ必要で、一般的な「年齢制限は書かない」
という原則の例外になります。

### 実行プラン

改善策は実施の重さで 3 つに分けて出します。着手の判断がしやすくなるためです。

- **今すぐできる** — 管理画面の設定変更だけで終わる
- **今週中に** — 原稿の書き換えが必要
- **クライアントに相談** — 条件そのものの見直しが必要

各グループの中は効果の大きい順です。あわせて「プランを一通りやりきった場合」の見込みも出します。
同じ段階の施策は効果が重なるので足し算せず、その段階で最も効くもの 1 つで見積もり、
段階をまたぐぶんだけ掛け算しています(各段階とも上位25%で頭打ちにします)。

最後に「次に効いてくる段階」を示します。CTR を直したら次は応募率が効いてくる、という順序が見えるためです。

考察は AI ではなく `lib/indeed/insight.ts` のロジックが書いています。同じ数字からは必ず同じ考察が出ます。
ファネル 3 段階の組み合わせから、求人が置かれている状態を 6 パターンに判定します。

| パターン | 意味 | 主な打ち手 |
|---|---|---|
| **見られていない** | 表示数が基準割れ | 予算・入札、タイトルの職種名と勤務地 |
| **選ばれていない** | 表示はあるが CTR が低い | 給与の見せ方、キャッチコピー、タイトル |
| **応募されていない** | クリックはあるが応募率が低い | 仕事内容の構成、応募フォーム、選考フロー |
| **条件で負けている** | CTR・応募率とも低い | 給与・休日など条件そのものの見直し |
| **詰まりなし** | 3 段階とも基準以上 | 予算を足して露出を伸ばす |
| **判定待ち** | 母数が足りない | もう 1 期間ぶん実績を貯める |

一覧画面には全求人をまとめた考察も出ます
(「5件のうち2件が『見られていない』— ここが最大の塊です」)。
同じ原因で詰まっている求人はまとめて直したほうが速いためです。

### 見込みの数字について

「上位25%まで行けます」とだけ言うのは過大な期待になるため、考察では
**基準並みまで戻した場合を本線**にし、上位25%は上振れたときの数字として添えています。
どちらも「他の段階が今のまま」という前提の単純計算であることも毎回明記します。

クリック率・応募率がまだ判定できる母数に達していない求人では、**応募増の試算そのものを出しません**。
ベンチマーク由来の率で応募数を計算しても、数字だけが独り歩きするためです。

## 何が「合理的」なのか

このツールの設計判断は 3 つです。

### 1. 数値の判断は AI にさせない

集計・ベンチマーク比較・ボトルネック特定・優先順位づけは、すべて `lib/indeed/` の決定論的な計算です。
AI が担当するのは、確定した診断結果を前提にした**言葉づくり**(キャッチコピー案・仕事内容案・お客様向け報告文)だけです。
そのため、同じデータからは毎回同じ診断が出ますし、AI が数字を作ることもありません。

### 2. 「率が一番悪いところ」ではなく「直すと応募が一番増えるところ」から並べる

CTR が半分でも表示数が 200 しかない求人より、CTR が 8 割でも表示数が 5 万ある求人のほうが、直したときのリターンは大きい。
そのため提案の並び順は次の式で決めています。

```
期待応募増 = min( 現在の月間応募数 × その施策の期待リフト率 , その段階を上位25%水準に戻したときの伸びしろ )
優先度     = 期待応募増 ÷ 実施の重さ × 段階の判定による重み
```

「段階の判定による重み」は、統計的に基準を下回っていると言い切れる段階(要改善)を、
ブレの範囲内の段階(標準)より優先するためのものです。

### 3. 母数が小さいときは「判定しない」と言う

表示 200 回・クリック 2 回で「CTR 1% だから要改善」と言うのはただのノイズです。
クリック率は表示 300 回以上、応募率はクリック 30 件以上を判定の最低ラインとし、
それ未満は **判定保留** として提案対象から外します。
判定にも Wilson 信頼区間を使い、「区間の上端が基準値を下回る = ブレではなく本当に低い」ときだけ要改善と判定します。

## どうやって学習するのか

学習は 2 系統あります。どちらも画面の「🧠 学習状況」タブで進み具合を数字で確認できます。

### ① 比較基準(ベンチマーク)の学習 — `lib/indeed/benchmark.ts`

「この業種のこの職種なら普通はこのくらい」という基準値を、登録済みの実績から作ります。

- **階層構造**: 業種 × 職種 × 雇用形態 → 業種 × 雇用形態 → 業種 → 全体 → 業種別の暫定値、と 4 段階で親をたどります。細かいセグメントのデータが少なくても、親のデータで補って推定できます
- **経験ベイズ収縮**: 各階層の推定値は「実測値」と「親の推定値」の加重平均で、重みはデータ量そのものです。**データが増えるほど自動的に実測寄りになります**。1 件目の登録から破綻せずに動き、蓄積が進むと自前の基準値に置き換わります
- **ハウスファクター**: 「暫定値がこの求人群に対して予測した数値」と「実際の数値」の比を取り、まだデータのない業種にも自分の事務所固有の上振れ・下振れを引き継ぎます
- **給与相場**: 登録済み求人から、同じ地域・同じ職種・同じ雇用形態の給与中央値を算出します。求人が増えるほど「相場より 21% 低い」という具体的な根拠つきで提案できるようになります

反映度は「累計表示数 ÷ (累計表示数 + 10,000)」で、累計 1 万表示でちょうど半分、10 万表示で 9 割が自社データに置き換わります。

### ② 施策効果の学習 — `lib/indeed/learn.ts`

ベンチマークが学ぶのは「何が普通か」。こちらが学ぶのは「**何をやると効くか**」です。

1. 求人の詳細画面で、実施した施策にチェックを入れて記録する
2. 施策日の前後 6 週間の実績を突き合わせ、CTR / 応募率 / 1日あたり表示数の相対リフトを測る
3. 施策ごとにリフトを集計し、初期値(カタログに書いた想定効果)から実測値へ徐々に置き換える
4. 提案の期待値と並び順に、その実測効果量を反映する

効果がなかった施策のマイナス値も学習に使われるため、**効かない施策は自動的に提案の上位から消えます。**

測定の扱いで気をつけている点:

- 同じ日に複数の施策を打つとどれが効いたか分離できないため、1/n の重みで按分します(画面上でも「1〜2 個ずつ打つと学習が速い」と案内しています)
- 統計的に有意でない観測も捨てずに使いますが、有意なものより重みを下げます(求人 1 件ごとの母数は小さく、有意なものだけでは学習が何年も進まないため)
- 極端な外れ値は丸めます(1 件の異常値で提案順が壊れないように)
- 施策日をまたぐ集計期間は、どちらの効果か分離できないため測定から除外します

## 業種ごとの提案

改善施策カタログ (`lib/indeed/playbook.ts`) には、表示数 7 件 / クリック率 9 件 / 応募率 12 件の施策が入っています。
各施策は「その求人で提案する根拠」を必ず返すため、提案は検証可能な指摘になります。

> ❌ 「CTR が低いのでタイトルを見直しましょう」
> ✅ 「タイトルに『小牧市』が入っていません。地名検索でヒットしにくい状態です」
> ✅ 「提示 1,100円 に対し、同セグメント 4 件の中央値は 1,400円。相場より 21% 低い水準です」
> ✅ 「キャッチコピーが全角 16 文字(上限 70 文字の 23%)。あと 54 文字ぶんの訴求枠が空いています」

業種は 15 種類(製造・軽作業 / 物流・運輸 / 介護・福祉 / 医療 / 飲食 / 販売・接客 / 事務 / 営業 / 建設・施工 / IT / 清掃・警備 / 保育・教育 / コールセンター / 美容・理容 / その他)で、
それぞれ「その業種の求職者が必ず気にすること」を持っています。応募率が低い求人では、その項目に原稿が答えているかを実際に照合して指摘します。

## 原稿チェックと法令対応

原稿(求人タイトル・キャッチコピー・仕事内容)を登録すると、機械的なチェックが走ります。判定基準は運用ルールに合わせています。

- キャッチコピー: 全角 70 文字以内 / 枠の使用率 / 給与・休日の記載 / 「20〜50代活躍中」/ 常套句の検出
- 仕事内容: ◆◆3ブロック構成 / 350 文字前後 / 1 行 24 文字以内 / ポイント 8 個以内 / 数字の有無
- 表現チェックは **法令** と **運用ルール** を分けて表示します
  - 法令: 年齢を限定する表現(「35歳まで」)、性別を限定・示唆する表現、断定的な誇大表現
  - 運用ルール: 「○○歓迎」→「○○活躍中」、「主婦」→「しゅふ / 主婦（夫）」

法令にふれうる表現は、**成果が良好な求人でも提案として必ず表示します**(成果とは別軸の問題のため)。

## Chrome で開く

このアプリは自分のパソコンで動かします(データも自分のパソコンの中だけに保存されます)。

**1. Node.js を入れる**(初回だけ)

<https://nodejs.org/ja> から LTS 版をダウンロードしてインストールします。
インストール済みかどうかは、ターミナル(Windows なら PowerShell)で `node -v` を実行して
`v20` 以上が表示されれば OK です。

**2. アプリを起動する**

```bash
git clone https://github.com/sho19910626/CLAUDE_CODE_GIT_BASH_PATH.git
cd CLAUDE_CODE_GIT_BASH_PATH
npm install     # 初回だけ(数分かかります)
npm run dev
```

**3. Chrome で開く**

<http://localhost:3000/indeed>

数字を 3 つ入れれば、すぐに診断が出ます。「サンプルを入れる」で試すこともできます。

`Ctrl + C`(Mac は `⌘ + C`)で停止します。次回からは `npm run dev` だけで起動できます。

> **APIキーは不要です。** 診断・考察・改善提案・学習はすべてブラウザとサーバー内の計算だけで動きます。
> 「✨ 改善案を作る」(AIによる原稿・報告文の作成)を使うときだけ、`.env` に `ANTHROPIC_API_KEY` が必要です。

### うまく動かないとき

| 症状 | 対処 |
|---|---|
| `npm: command not found` | Node.js が入っていません。手順 1 に戻ってください |
| `Error: listen EADDRINUSE :::3000` | 3000番ポートが使用中です。`npm run dev -- -p 3001` で別のポートで起動してください |
| ページが真っ白 | ターミナルにエラーが出ていないか確認してください。`npm install` のやり直しで直ることが多いです |
| データが消えた | ブラウザの履歴・サイトデータを消すと一緒に消えます。定期的に「💾 書き出し」でバックアップを取ってください |

### データはどこにありますか

Chrome の localStorage(キー `indeed-analytics-v1`)に保存されます。
**同じパソコンの同じ Chrome でのみ見えます。** シークレットウィンドウでは保存されません。
別のパソコンや別のブラウザで使いたいときは、「💾 書き出し」で JSON を保存して
「📂 読み込み」で取り込んでください。

## 記録して学習させる版の使い方 (`/indeed/manage`)

1. **📥 実績を取り込む** — Indeed の管理画面やスプレッドシートで表を選択してコピーし、そのまま貼り付けます
   - 必須列: 求人名 / 表示数 / クリック数 / 応募数(1 行目を見出し行に)
   - 任意列: 会社名 / 業種 / 職種 / 雇用形態 / 都道府県 / 時給 / 期間 / 費用
   - タブ区切り(コピペ)と CSV の両方、「1,234」「¥5,000」「12.3%」といった書式付きの数値にも対応します
   - CTR・応募率の列は読み込みますが、値は表示数・クリック数・応募数から計算し直します(食い違えば警告します)
   - 同じ求人・同じ期間のデータは上書きされるため、毎月同じ表を貼り直しても二重計上になりません
2. **📊 求人一覧・診断** — 求人をクリックすると、ファネル図・段階別の判定・改善提案が出ます
3. **求人を編集** — 原稿・給与・応募フォームの設問数などを登録すると、提案が具体的になります
4. **施策を記録** — 実施した提案にチェックを入れて記録します。**これがツールの精度を上げる唯一の入力です**
5. **✨ 改善案を作る** — 診断結果をもとに、キャッチコピー案・仕事内容のリライト案・お客様向け報告文を AI が作成します
6. **🧠 学習状況** — ベンチマークの反映度と、施策ごとの実測効果を確認できます

## 精度を上げるためにやること

1. **毎月、実績を登録する** — ベンチマークが自社データに置き換わり、前後比較による効果測定もできるようになります
2. **職種名の表記を揃える** — 「フォークリフト」と「フォークリフト作業」は別セグメント扱いです。揃えるほど細かい粒度で比較できます
3. **原稿を登録する** — 提案が「CTRが低い」から「キャッチが 38 文字しか使えていない」に変わります
4. **施策は 1〜2 個ずつ打って記録する** — 同時に 5 個変えると、どれが効いたか分離できません
5. **効果がなかった施策も記録する** — マイナスの実測値も学習に使われます
6. **定期的に「💾 書き出し」でバックアップを取る** — 蓄積が消えると精度も戻ってしまいます

## データの保存について

データはブラウザの `localStorage`(キー `indeed-analytics-v1`)に保存されます。サーバーには送信されません
(AI 提案を実行したときだけ、その求人 1 件ぶんの情報が Anthropic API に送られます)。

端末をまたいで使う場合や、バックアップを取る場合は **💾 書き出し / 📂 読み込み** の JSON を使ってください。
読み込みは既存データへの統合(マージ)なので、複数人ぶんのデータを 1 つにまとめることもできます。

複数人でリアルタイムに共有したくなった場合は、`lib/indeed/store.ts` の `readStore` / `writeStore` を
サーバー API に差し替えるだけで移行できます(画面側はこのファイル経由でしかデータに触れていません)。

## ベンチマークの初期値について

> ⚠️ `lib/indeed/seed.ts` の数値は **実データが 1 件もないときだけ使う暫定の初期値**です。
> 求人媒体の成果は同じ業種でもエリア・予算・時期で大きく振れるため、この値そのものを正解として扱ってはいけません。
> 実績を登録するほど自分のデータで置き換わっていき、初期値の影響は自動的に薄まります。
> 画面には常に「暫定値 / 実データ何件から算出」を表示しているので、判定の根拠がどちらなのかは毎回確認できます。
